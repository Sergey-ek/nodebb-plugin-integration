# Справочник MCP API

Версия: 0.6.2

## 1. Обзор

Плагин предоставляет функциональность NodeBB через Model Context Protocol (MCP), используя транспорт Streamable HTTP.

Адрес MCP:

```text
/mcp
```

MCP-сервер работает в отдельном дочернем процессе, управляемом плагином NodeBB. Взаимодействие с NodeBB осуществляется через внутренний HTTP API, защищённый отдельным автоматически генерируемым токеном аутентификации.

Плагин поддерживает два режима аутентификации MCP-клиентов:

- **OAuth 2.0** — режим по умолчанию. Каждый клиент авторизует конкретного пользователя NodeBB и работает с его правами доступа.
- **Legacy Bearer Token** — режим обратной совместимости, в котором все клиенты используют один статический токен и работают от имени настроенного служебного пользователя NodeBB.

Архитектура:

```text
MCP client
    |
    | Streamable HTTP
    | OAuth access token OR legacy Bearer token
    v
MCP child process
    |
    | Internal HTTP API
    | Separate internal authentication token
    v
NodeBB integration plugin
    |
    | User-scoped NodeBB API calls
    | Native permission checks
    v
NodeBB
```

Плагин предоставляет 15 MCP-инструментов для получения информации о форуме, чтения, поиска и управления содержимым.

Все операции выполняются с учётом прав доступа NodeBB пользователя, от имени которого выполняется запрос.

Инструмент `search_knowledge` дополнительно требует провайдера OpenAI и настроенного экземпляра Qdrant.

## 2. Настройка

Настройки MCP управляются через:

**NodeBB ACP → Plugins → NodeBB Integration**

| Параметр | Описание |
|---|---|
| Enable MCP | Включение или отключение MCP-сервера |
| Authentication mode | Режим аутентификации: OAuth 2.0 или Legacy Bearer Token |
| Bind address | Сетевой интерфейс, на котором MCP HTTP-сервер принимает подключения |
| Port | Порт MCP HTTP-сервера |
| NodeBB URL | Внутренний URL для подключения MCP-процесса к NodeBB |
| Bearer token | Общий токен аутентификации клиентов; используется только в режиме Legacy Bearer |
| Service user UID | Учётная запись NodeBB, от имени которой выполняются операции MCP; используется только в режиме Legacy Bearer |

Настройки подключения по умолчанию:

```text
Bind address: 127.0.0.1
Port:         3100
NodeBB URL:   http://127.0.0.1:4567
```

Адрес привязки по умолчанию ограничивает подключения к MCP локальным интерфейсом. Изменяйте его только в том случае, если удалённый доступ действительно необходим и сетевой периметр надёжно защищён.

При публикации MCP через обратный прокси внешний адрес `/mcp` должен быть доступен по HTTPS.

Плагин автоматически генерирует отдельный случайный токен для своего внутреннего API. Этот токен используется только для взаимодействия между дочерним MCP-процессом и плагином NodeBB. Он отличается от учётных данных MCP-клиентов и никогда не должен передаваться MCP-клиентам.

### Режим аутентификации

OAuth 2.0 является режимом аутентификации по умолчанию.

В режиме OAuth:

- Каждый MCP-клиент авторизует отдельного пользователя NodeBB.
- Операции MCP выполняются с UID аутентифицированного пользователя.
- Права доступа NodeBB проверяются для этого пользователя.
- Параметры общего MCP Bearer-токена и Service user UID не используются.

Режим Legacy Bearer Token доступен для обратной совместимости.

В режиме Legacy Bearer:

- Все MCP-клиенты используют один и тот же настроенный статический Bearer-токен.
- Операции MCP выполняются с UID настроенного Service user.
- Права доступа NodeBB проверяются для этого служебного пользователя.

При использовании режима Legacy Bearer параметр Service user UID должен указывать на существующего пользователя NodeBB.

## 3. Аутентификация и права доступа

### 3.1. OAuth 2.0

OAuth 2.0 является режимом аутентификации по умолчанию.

Плагин реализует поток OAuth 2.0 Authorization Code с PKCE, используя метод проверки кода `S256`.

MCP-клиенты являются публичными клиентами и не используют `client_secret`.

#### Метаданные сервера авторизации

Метаданные OAuth-сервера авторизации публикуются по адресу:

```text
https://forum.example.com/.well-known/oauth-authorization-server
```

В метаданных указываются следующие конечные точки:

| Назначение | Путь |
|---|---|
| Авторизация | `/oauth/authorize` |
| Получение токена | `/oauth/token` |
| Отзыв токена | `/oauth/revoke` |
| Метаданные сервера авторизации | `/.well-known/oauth-authorization-server` |

Поддерживаемая область доступа (scope):

```text
mcp
```

Сервер поддерживает следующие типы предоставления разрешений (grant types):

- `authorization_code`
- `refresh_token`

Метод аутентификации на конечной точке токенов — `none`, поскольку MCP-клиенты являются публичными клиентами.

PKCE с методом `S256` обязателен.

#### Идентификация клиентов и метаданные

Плагин поддерживает Client ID Metadata Documents (CIMD).

Клиент идентифицирует себя с помощью HTTPS URL, используемого в качестве `client_id`. Этот URL указывает на документ с метаданными OAuth-клиента.

Документ метаданных должен соответствовать следующим требованиям:

- `client_id` должен совпадать с URL документа метаданных.
- Поле `client_name` обязательно.
- `redirect_uris` должен содержать от 1 до 20 корректных URI перенаправления.
- URI перенаправления должны использовать HTTPS или разрешённый HTTP loopback-адрес.
- HTTP loopback-перенаправления разрешены для нативных приложений, использующих `localhost`, `127.0.0.1` или `[::1]`.
- Поле `client_secret` не должно передаваться.
- `token_endpoint_auth_method` должен иметь значение `none`.
- `response_types` должен содержать `code`.
- `grant_types` должен включать `authorization_code`. Также поддерживается `refresh_token`.

Документ метаданных загружается по HTTPS.

В целях безопасности механизм загрузки метаданных:

- Отклоняет имена хостов, заданные IP-адресами напрямую.
- Выполняет разрешение имени хоста и требует, чтобы полученные IP-адреса относились к публичным unicast-адресам.
- Привязывает проверенный DNS-результат к соединению для защиты от DNS rebinding.
- Проверяет TLS-сертификаты.
- Использует тайм-аут 5 секунд.
- Ограничивает размер тела ответа 64 КиБ.
- Требует HTTP-ответ со статусом 200 и JSON Content-Type.

#### Согласие пользователя и авторизация клиента

Когда пользователь подключает новый OAuth-клиент:

1. Плагин загружает и проверяет документ метаданных клиента.
2. Пользователь проходит аутентификацию в NodeBB.
3. NodeBB отображает страницу явного подтверждения доступа.
4. После подтверждения пользователем клиент автоматически получает разрешение на работу от имени этого пользователя.

Для ранее одобренного клиента повторное подтверждение не требуется, пока его разрешение на доступ и метаданные клиента остаются действительными. Если разрешение отозвано или метаданные клиента изменились, пользователь должен повторно подтвердить авторизацию.

Для нового клиента обязательно явное подтверждение пользователя.

Каждый авторизованный клиент связан с пользователем NodeBB, который предоставил ему доступ. Операции MCP выполняются с UID и правами доступа этого пользователя.

#### Срок действия и обновление токенов

OAuth-токены представляют собой непрозрачные значения. В Redis сохраняются хеши токенов, а не их исходные значения.

| Токен | Срок действия |
|---|---|
| Код авторизации | 5 минут |
| Токен доступа | 15 минут |
| Токен обновления | 30 дней |

При использовании токены обновления заменяются новыми.

Плагин отслеживает семейства токенов обновления и обнаруживает повторное использование ранее заменённых токенов. При обнаружении такого повторного использования соответствующее семейство токенов отзывается.

#### Управление доступом и отзыв авторизации клиентов

Пользователи могут управлять доступом MCP на странице своей учётной записи NodeBB:

```text
/user/<userslug>/integration
```

На этой странице пользователи могут:

- Включать и отключать доступ MCP целиком.
- Просматривать авторизованные MCP-клиенты.
- Отзывать разрешение отдельного клиента.

Отключение доступа MCP на уровне пользователя аннулирует существующие OAuth-токены.

Повторное включение доступа не восстанавливает ранее аннулированные токены. Клиенты должны пройти авторизацию заново.

Конечная точка отзыва OAuth-токенов:

```text
POST /oauth/revoke
```

### 3.2. Legacy Bearer Token

Режим Legacy Bearer Token предусмотрен для обратной совместимости.

Клиенты проходят аутентификацию, передавая настроенный общий токен в HTTP-заголовке Authorization:

```http
Authorization: Bearer YOUR_MCP_TOKEN
```

Все клиенты, использующие этот токен, работают от имени пользователя NodeBB, указанного в параметре Service user UID.

Права доступа этого служебного пользователя в NodeBB определяют, какие операции разрешены.

Используйте этот режим только в том случае, если требуется совместимость с существующей интеграцией, использующей Bearer-токен.

### 3.3. Аутентификация внутреннего API

Дочерний MCP-процесс взаимодействует с плагином NodeBB через закрытый внутренний HTTP API.

Для этого API используется отдельный автоматически генерируемый токен аутентификации.

Внутренний токен:

- Отличается от OAuth-токенов доступа и Legacy MCP Bearer-токена.
- Используется только для взаимодействия между дочерним MCP-процессом и плагином NodeBB.
- Никогда не должен передаваться внешним MCP-клиентам.

Внутренние маршруты API требуют аутентификации и отключаются при отключении MCP.

В режиме OAuth плагин проверяет личность аутентифицированного пользователя перед выполнением операций MCP.

### 3.4. Пользователь, от имени которого выполняется запрос, и права доступа

Пользователь, от имени которого выполняется запрос, зависит от настроенного режима аутентификации:

| Режим аутентификации | Пользователь, от имени которого выполняются операции |
|---|---|
| OAuth 2.0 | Пользователь NodeBB, авторизовавший MCP-клиент |
| Legacy Bearer Token | Пользователь NodeBB, указанный в параметре Service user UID |

Операции чтения и записи используют штатные API NodeBB и встроенные проверки прав доступа.

Клиент не может подменить UID пользователя, от имени которого выполняется запрос.

Аргумент `uid` инструмента `delete_user_posts` определяет целевую учётную запись, сообщения которой необходимо удалить. Он не изменяет пользователя, от имени которого выполняется операция.

### 3.5. Доступ к содержимому и конфиденциальность

Операции чтения учитывают проверки доступа NodeBB.

Пользователь может получать только то содержимое, к которому имеет доступ учётная запись, от имени которой выполняется запрос.

Результаты семантического поиска также фильтруются с учётом прав доступа этого пользователя. Одного лишь векторного сходства недостаточно для предоставления доступа к сообщению или теме.

Перед возвратом содержимого сообщения плагин проверяет полученные метаданные по данным NodeBB.

Инструмент `get_user` возвращает только выбранные публичные поля профиля. Он не раскрывает конфиденциальную информацию учётной записи.

## 4. Общие правила аргументов

- Идентификаторы должны быть положительными безопасными целыми числами.
- Смещения пагинации должны быть неотрицательными целыми числами.
- Неизвестные аргументы отклоняются.
- Дополнительные свойства отклоняются.
- Текстовые аргументы не должны быть пустыми или состоять только из пробельных символов.
- Ограничения длины текста измеряются в символах строк JavaScript.
- Аргументы инструментов должны представлять собой JSON-объекты.

MCP-сервер возвращает результаты инструментов в виде форматированного JSON-текста. Ошибки возвращаются как результаты MCP-инструментов с `isError: true`.

## 5. Справочник инструментов

### 5.1. get_forum_info

Возвращает общедоступную информацию о форуме.

Аргументы: отсутствуют.

Пример:

```json
{}
```

Поля ответа:

| Поле | Тип | Описание |
|---|---|---|
| title | string | Название форума |
| url | string | URL форума |
| version | string | Версия NodeBB |
| language | string or null | Язык форума |

Пример:

```json
{
  "title": "Example Forum",
  "url": "https://forum.example.com",
  "version": "4.16.8",
  "language": "en-GB"
}
```

### 5.2. get_post

Получает сообщение по его идентификатору после проверки того, что пользователь, от имени которого выполняется запрос, может читать как само сообщение, так и его тему.

Аргументы:

| Имя | Тип | Обязательный | Ограничения |
|---|---|---|---|
| pid | integer | Да | Минимум 1 |

Пример:

```json
{
  "pid": 123
}
```

Ответ:

| Поле | Тип | Описание |
|---|---|---|
| pid | integer | ID сообщения |
| tid | integer | ID темы |
| uid | integer | UID автора |
| cid | integer | ID категории |
| content | string | Содержимое сообщения |
| timestamp | NodeBB timestamp | Время создания сообщения |

Удалённые сообщения, отсутствующие сообщения и сообщения, недоступные пользователю, от имени которого выполняется запрос, возвращаются как не найденные.

### 5.3. get_topic

Получает метаданные темы после проверки прав доступа на её чтение.

Аргументы:

| Имя | Тип | Обязательный | Ограничения |
|---|---|---|---|
| tid | integer | Да | Минимум 1 |

Пример:

```json
{
  "tid": 42
}
```

Ответ:

| Поле | Тип | Описание |
|---|---|---|
| tid | integer | ID темы |
| uid | integer | UID автора темы |
| title | string | Название темы |
| cid | integer | ID категории |
| timestamp | NodeBB timestamp | Время создания темы |
| mainPid | integer | ID первого сообщения |

Инструмент возвращает метаданные темы, а не полный список её сообщений. Для получения сообщений используйте `list_posts`.

### 5.4. get_user

Возвращает общедоступную информацию профиля пользователя.

Аргумент `uid` определяет пользователя, публичный профиль которого необходимо получить. Он не изменяет пользователя, от имени которого выполняется запрос, и не определяет учётную запись, от которой выполняются операции.

Аргументы:

| Имя | Тип | Обязательный | Ограничения |
|---|---|---|---|
| uid | integer | Да | Минимум 1 |

Пример:

```json
{
  "uid": 7
}
```

Ответ:

| Поле | Тип | Описание |
|---|---|---|
| uid | integer | ID пользователя |
| username | string | Имя пользователя |
| userslug | string | Имя пользователя в формате URL |
| picture | string | URL аватара или значение, предоставленное NodeBB |

Возвращаются только перечисленные выше поля.

### 5.5. search_knowledge

Выполняет семантический поиск по проиндексированной базе знаний форума.

Требует провайдера OpenAI и работающей коллекции Qdrant.

Аргументы:

| Имя | Тип | Обязательный | Ограничения |
|---|---|---|---|
| query | string | Да | 1–2000 символов |
| limit | integer | Нет | 1–20; по умолчанию 5 |

Пример:

```json
{
  "query": "How do I configure forum notifications?",
  "limit": 5
}
```

Ответ:

```json
{
  "results": [
    {
      "pid": 123,
      "tid": 42,
      "uid": 7,
      "cid": 3,
      "score": 0.91,
      "content": "Post content..."
    }
  ]
}
```

Поля результата:

| Поле | Тип | Описание |
|---|---|---|
| pid | integer | ID сообщения |
| tid | integer | ID темы |
| uid | integer | UID автора |
| cid | integer | ID категории |
| score | number | Оценка семантического сходства, полученная при векторном поиске |
| content | string | Содержимое сообщения, полученное из NodeBB |

Алгоритм поиска:

1. Генерируется эмбеддинг поискового запроса.
2. В Qdrant выполняется поиск подходящих сообщений-кандидатов.
3. Проверяются исключения для категорий-кандидатов.
4. Проверяются права пользователя на чтение сообщений и тем.
5. Из NodeBB извлекается содержимое разрешённых сообщений.
6. Возвращается не более запрошенного количества подходящих результатов.

Для компенсации фильтрации по правам доступа реализация может извлекать больше кандидатов, чем указано в параметре `limit`.

В режиме Fake AI инструмент возвращает ошибку об отключённом ИИ. Семантический поиск в этом режиме не выполняется.

### 5.6. create_topic

Создаёт тему в категории NodeBB от имени пользователя, выполняющего запрос.

Аргументы:

| Имя | Тип | Обязательный | Ограничения |
|---|---|---|---|
| cid | integer | Да | Минимум 1 |
| title | string | Да | 1–255 символов |
| content | string | Да | 1–20000 символов |
| tags | array of strings | Нет | Не более 10 тегов; каждый длиной 1–32 символа |

Пример:

```json
{
  "cid": 3,
  "title": "New discussion",
  "content": "The opening post content.",
  "tags": ["discussion", "help"]
}
```

Если `tags` не указан, используется пустой массив.

Перед отправкой заголовок очищается от пробелов в начале и конце. Содержимое передаётся в NodeBB без удаления пробелов.

NodeBB выполняет проверки прав доступа к категории, ограничений на публикацию, корректности тегов и вызывает штатные хуки создания.

Ответ содержит результат, возвращённый штатным методом создания темы NodeBB.

### 5.7. delete_topic

Выполняет мягкое удаление темы с использованием штатных проверок прав доступа и хуков NodeBB.

Аргументы:

| Имя | Тип | Обязательный | Ограничения |
|---|---|---|---|
| tid | integer | Да | Минимум 1 |

Пример:

```json
{
  "tid": 42
}
```

Это операция мягкого удаления, а не безвозвратное удаление.

Ответ содержит результат штатной операции NodeBB.

### 5.8. restore_topic

Восстанавливает ранее мягко удалённую тему.

Аргументы:

| Имя | Тип | Обязательный | Ограничения |
|---|---|---|---|
| tid | integer | Да | Минимум 1 |

Пример:

```json
{
  "tid": 42
}
```

NodeBB проверяет права пользователя, от имени которого выполняется запрос, и запускает штатные хуки восстановления.

Восстановление темы не приводит к автоматическому восстановлению сообщений, которые были удалены отдельно.

Ответ содержит результат штатной операции NodeBB.

### 5.14. delete_user_posts

Выполняет мягкое удаление ответов, написанных указанным пользователем.

Первое сообщение каждой темы всегда пропускается. Инструмент не удаляет основные сообщения тем.

Аргументы:

| Имя | Тип | Обязательный | Ограничения |
|---|---|---|---|
| uid | integer | Да | UID целевого пользователя; минимум 1 |
| start | integer | Нет | 0–10000000; по умолчанию 0 |
| limit | integer | Нет | 1–100; по умолчанию 100 |

Пример:

```json
{
  "uid": 25,
  "start": 0,
  "limit": 100
}
```

Удаление выполняет пользователь, от имени которого запущен запрос. Переданный `uid` определяет только целевого автора сообщений.

Операция обрабатывает сообщения последовательно и продолжает работу даже при отдельных ошибках удаления.

Ошибки отдельных операций удаления включаются в массив `failed`. Сами по себе такие ошибки не останавливают обработку оставшихся сообщений и не означают, что весь вызов инструмента завершился неудачно.

Сообщения пропускаются, если они некорректны, отсутствуют, уже удалены, больше не принадлежат целевому пользователю или являются основным сообщением темы.

Ответ:

| Поле | Тип | Описание |
|---|---|---|
| uid | integer | UID целевого пользователя |
| scanned | integer | Количество ID, возвращённых для текущей страницы |
| deleted | integer | Количество успешно мягко удалённых ответов |
| skipped | integer | Количество пропущенных сообщений |
| failed | array | Ошибки отдельных операций удаления |
| hasMore | boolean | Заполнена ли полученная страница ID до запрошенного лимита |
| nextStart | integer | Рекомендуемое смещение для следующей порции |

Каждый элемент `failed` содержит:

```json
{
  "pid": 123,
  "error": "Permission denied"
}
```

Пример ответа:

```json
{
  "uid": 25,
  "scanned": 100,
  "deleted": 85,
  "skipped": 10,
  "failed": [
    {
      "pid": 456,
      "error": "Permission denied"
    }
  ],
  "hasMore": true,
  "nextStart": 15
}
```

Пример приведён для иллюстрации. Фактические значения счётчиков зависят от полученных ID и результатов операций.

#### Пакетная обработка

Используйте значение `nextStart` из предыдущего ответа в качестве `start` следующего запроса:

```json
{
  "uid": 25,
  "start": 15,
  "limit": 100
}
```

Успешно удалённые сообщения исключаются из активного списка сообщений пользователя. Реализация корректирует `nextStart`, вычитая количество успешно удалённых сообщений, чтобы не пропустить оставшиеся ответы.

Значение `hasMore` определяется тем, содержит ли текущая страница ID полное запрошенное количество элементов. Это подсказка для пагинации; следующий запрос может вернуть пустую страницу.

Эта операция не выполняет безвозвратную очистку данных. Основные сообщения тем этим инструментом никогда не удаляются.

## 6. Пагинация

Инструменты получения списков используют смещения, начинающиеся с нуля.

| Инструмент | Начальное значение start | Лимит по умолчанию | Максимальный лимит |
|---|---:|---:|---:|
| list_topics | 0 | 20 | 100 |
| list_posts | 0 | 20 | 100 |
| delete_user_posts | 0 | 100 | 100 |

Для инструментов получения списков, если `hasMore` равно `true`, используйте возвращённое значение `nextStart` в следующем запросе.

При пакетном удалении всегда используйте возвращённое значение `nextStart`, поскольку успешное удаление изменяет активный список сообщений.

## 7. Ошибки

MCP-сервер возвращает ошибки выполнения в виде текста с `isError: true`.

Распространённые ситуации:

| Ситуация | Поведение |
|---|---|
| Некорректные аргументы | Ошибка проверки аргументов инструмента |
| Неизвестный или лишний аргумент | Запрос отклоняется |
| Некорректный ID | Запрос отклоняется |
| MCP отключён | Внутренний API отклоняет запрос |
| Некорректный внутренний токен | Внутренний API возвращает ошибку Unauthorized |
| Отсутствующее или недоступное сообщение/тема | При защищённом чтении возвращается статус «не найдено» |
| Отказ в разрешении NodeBB | Ошибка штатной операции NodeBB |
| ИИ-провайдер отключён | Семантический поиск недоступен |
| Ошибка внутренней операции | Инструмент возвращает ошибку |

Для `search_knowledge` режим с отключённым ИИ приводит к явной ошибке. Другие сбои инфраструктуры поиска также возвращаются как ошибки.

Пакетное удаление отличается от операций с одним элементом: отдельные ошибки собираются в массиве `failed`, а обработка следующих ID продолжается.

## 8. Безопасность и эксплуатационные рекомендации

- Используйте отдельную служебную учётную запись NodeBB только с теми правами, которые необходимы для предполагаемых операций.
- Не публикуйте внутренний токен API MCP.
- Используйте привязку к `127.0.0.1`, если удалённый доступ не требуется.
- При удалённой публикации MCP используйте защищённый сетевой канал.
- Инструменты удаления выполняют мягкое удаление, а не безвозвратную очистку данных.
- `delete_user_posts` пропускает основные сообщения тем.
- Восстановление темы не восстанавливает отдельно удалённые сообщения.
- Семантический поиск возвращает только сообщения, доступные пользователю, от имени которого выполняется запрос.
- Плагин не доверяет UID пользователя, переданному клиентом.

## 9. Совместимость

Плагин предназначен для NodeBB 4.x и требует Node.js >= 22.

Реализация версии 0.6.2 проверялась с NodeBB 4.16.8.

Набор полей в ответах штатных методов NodeBB может различаться в зависимости от версии NodeBB. Для создания, редактирования, удаления, восстановления и получения списков плагин использует штатные методы NodeBB.
